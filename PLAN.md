# StarStocks — план обновления и разбор предложений

Основано на фактах из [AUDIT.md](./AUDIT.md) (проверено живым запуском). Ничего не генерировал — только решения.

## Принципы, на которых строим

1. **Сервер — единственный источник истины** для портфеля, заявок, доходности. Клиент только отображает.
2. **Каждая цифра имеет источник и время.** Любая котировка/метрика несёт `source` и `asOf`; задержка (MOEX ~15 мин) показывается честно.
3. **Никаких платных и хрупких источников на старте**, но слой доступа к данным — сменяемый (провайдеры + fallback).
4. **Сначала чиним, потом украшаем.** Тема, скелетоны и соцсеть бесполезны, пока БД не работает и пароли утекают.
5. Один процесс, in-memory кэш — пока пользователей мало. Но интерфейс кэша готов к Redis.

## Разбор каждого предложения

### 1. Bcrypt для паролей — «когда автор будет готов»

**Вердикт: делать сразу, но иначе.**

Сейчас пароль лежит в БД открытым текстом и уходит в ответах API и в `localStorage` (P0-2). Это не «фича, до которой дойдём», а дыра: пять существующих паролей уже скомпрометированы по определению, их надо считать сгоревшими и заставить пользователей сменить.

Но bcrypt — не единственный путь, и я бы выбрал другой:

| Вариант | Плюсы | Минусы | Оценка |
|---|---|---|---|
| **Supabase Auth** (рекомендую) | готово: JWT, подтверждение почты, сброс пароля, RLS, OAuth; `@supabase/ssr` уже в зависимостях; bcrypt не нужен вообще | логика на стороне Supabase, меньше контроля | 1–2 дня |
| `bcrypt` + свои сессии (httpOnly cookie + JWT) | полный контроль, данные у себя | надо писать всё: сессии, восстановление, CSRF | 3–5 дней |
| bcrypt без сессий | быстро | бесполезно: авторизация всё равно отсутствует | 0.5 дня, не решает |

Если остаёмся на своей таблице — обязательно bcrypt с cost ≥ 12, сессии в httpOnly-cookie, `/api/auth/*` с rate limit, ответы без `password`, миграция 5 старых пользователей через сброс пароля.

### 2. Динамика мультипликаторов (P/E) во времени — график, а не заглушка

**Вердикт: делать, но исторических P/E «из коробки» бесплатно почти нет.**

Варианты источника:

| Источник | Что даёт | Цена | Реалистичность |
|---|---|---|---|
| Реконструкция: `P/E(t) = цена(t) / EPS_TTM(t)` из квартальных отчётов (Finnhub `/stock/earnings`, бесплатно) + свои свечи | честная «оценка P/E», 8–12 кварталов | 0 | высокая, но точность приблизительная — надо так и подписать |
| Financial Modeling Prep / EOD Historical `/ratios` | готовые исторические P/E | ~$20–100/мес | точнее, но платно |
| Yahoo – только текущее | не исторично | 0 | не подходит |

**Рекомендация:** реконструкция + метка «оценка, EPS TTM по квартальным отчётам», с датой обновления. Если точность критична — обсудить платную подписку, но это уже осознанное решение о бюджете.
Важно: P/E по годам лучше рисовать с текущим P/E и медианой сектора — иначе линия из точек нечитаема.

Объём: **M** (1–2 дня на расчёт + 1 день на интеграцию в UI).

### 3. Сравнение акций — таблица двух тикеров рядом

**Вердикт: делать, но не только таблицей.**

Таблица — дёшево (данные уже есть), но ценность появляется, когда рядом есть **нормализованный график**: `Δ%` от начала периода, чтобы сравнивать акции с ценами $5 и $500. Плюс нормализация валют (EUR/RUB → USD по курсу ЦБ/ECB).

Минимум: таблица 15–20 метрик + строка «лучше/хуже» по каждой + недельная/месячная динамика.
Хорошо: наложение двух линий, режим «спред» (relative performance), сохранение пары в избранное.

Объём: **S** для таблицы, **M** с графиком. Зависит от пункта 12 (валюты).

### 4. Подсказки по каждому показателю + информация о компаниях

**Вердикт: делать. Это самая недооценённая идея списка — она превращает калькулятор в учебный продукт.**

Трудозатраты — в основном **контент, а не код**:
- глоссарий-справочник: для каждого показателя 5 полей — что это, как считается, что показывает, как применять, типичные ловушки + отраслевые нормы;
- перечень: P/E, P/S, EV/EBITDA, EBITDA margin, ROE, Debt/EBITDA, Rev growth, RSI, MACD, SMA50/200, объём, волатильность, дивидендная доходность, P/B, FCF yield;
- данные компании: описание, сектор, страна, капитализация, число сотрудников, сайт — Finnhub `/stock/profile2` (бесплатно), текст — свой.

Технически: один JSON-файл `glossary.json` + один компонент попапа (клик по названию метрики, `Esc`/клик мимо — закрыть, доступность с клавиатуры). Компании — кнопка «О компании» на карточке тикера.

Критично: **не выдумывать цифры** в справочнике, формулировки держать нейтральными и с оговоркой «не индивидуальная инвестиционная рекомендация».

Объём: **S** код (1–2 дня), **L** контент (можно итеративно: начать с 8 главных метрик).

### 5. Дизайн графиков «как TradingView»

**Вердикт: делать, но это смена библиотеки, а не косметика.**

Сейчас три библиотеки одновременно: Chart.js (CDN), CanvasJS StockChart + jQuery (CDN, jQuery 2014 года). CanvasJS StockChart **платный для коммерческого использования** и плохо кастомизируется под «как в TradingView».

Правильный путь: **lightweight-charts** (TradingView, Apache-2.0, бесплатно). Даёт из коробки: свечи/бары/линия/площадь, объёмы, кроссхэйр с ценой на оси, лог-шкалу, ресайз, панель индикаторов, плавное масштабирование. Ровно то, что просится.

Что уйдёт: CanvasJS, jQuery, CDN-зависимости, `theme: "dark2"` в двух местах, статичный гейдж.
Что появится: свечи + объём + скользящие, тулбар таймфреймов (1D/1W/1M/1Y), сохранение выбранного ТФ, корректная тема.

Объём: **M** (2–3 дня) — включая перенос радара на нормальный gauge.

### 8. WebSocket для крипты через Binance

**Вердикт: делать. Это заодно чинит крипту, которая сейчас не работает вообще** (невалидный ключ FCS, P1-2).

Проверено: `api.binance.com` и `data-api.binance.vision` доступны, `BTCUSDT` = 59 611.

Что учесть:
- комбинированный стрим `wss://stream.binance.com:9443/stream?streams=btcusdt@trade/ethusdt@trade/...`, реконнект с экспоненциальным backoff, heartbeat;
- **не broadcast всем клиентам**: протокол подписки `{action:'subscribe', symbols:[...]}` — иначе на 10 монетах сервер захлебнётся трейдами (сейчас шлёт всё всем без троттлинга);
- троттлинг: склеивать тики до 4–10 сообщений/сек на клиента;
- fallback на REST `ticker/24hr` при обрыве, чтобы UI не замирал (сейчас замирает навсегда — P0-6);
- **геориск:** Binance ограничивает доступ из ряда регионов; предусмотреть альтернативу (Bybit/OKX/Kraken WS) за тем же интерфейсом. Прямо из РФ `stream.binance.com` может не открыться — проверить на целевой машине;
- крипта — это спот-трейды, не «котировка акции»: объём, 24h-изменение и время сделки надо показывать отдельно.

Объём: **M** (2–3 дня, включая подписки и реконнект).

### 9. Кэширование в Redis — «если пользователей станет много»

**Вердикт: сейчас — нет. Позже — да, но не первым делом.**

При одном процессе и десятках пользователей Redis не даёт ничего, кроме операций. Реальные проблемы кэша сейчас другие (P1-10): нет склейки одновременных запросов, ошибки не кэшируются, TTL не соответствует данным, свечи на год держатся 60 секунд.

Что делать сейчас (дёшево, 0.5 дня):
- слой `cache` с интерфейсом `get/set/del/getOrLoad`;
- **single-flight**: один запрос на ключ, остальные ждут результат;
- TTL по типу: котировки 10–60 с, свечи 1 ч, фундаментал 24 ч, новости 10 мин, профиль компании 7 дней;
- negative caching на 30–60 с для 404/429 (иначе битый тикер долбит API);
- метрики попаданий/промахов.

Redis подключать, когда появится: второй инстанс, отдельный воркер для WS/ордеров, или общий кэш между API и сокетами. Замена будет стоить полдня, если интерфейс сделан заранее.

### 12. «Реальные аккаунты, сообщества, посты, сообщения, поиск по id»

**Вердикт: аккаунты — немедленно (это P0). Сообщества/посты/ЛС — отдельный этап, и я бы сузил их.**

Разбор по частям:

| Часть | Решение | Почему |
|---|---|---|
| Реальные аккаунты | **делать в первую очередь** | без этого остальное небезопасно; Supabase Auth закрывает вопрос |
| Поиск по id | **делать, дёшево** | но только публичный `username`/handle, никогда не email; rate limit; лучше «поиск по нику» |
| Посты (лента) | **позже, с модерацией** | без модерации это спам-помойка за неделю; нужны лимиты, жалобы, удаление, антиспам |
| Личные сообщения | **позже всех / возможно не делать** | абьюз, жалобы, приватность, шифрование, юридика; в финпродукте почти не дают ценности |
| Сообщества | **делать, но в форме «клубов стратегий»** | не универсальная соцсеть, а клубы вокруг портфелей/стратегий — это опирается на данные, которые уже есть |

Что реально ценно и дешевле, чем соцсеть: **публичный портфель по ссылке** (только чтение, скрытие сумм), **комментарии к сделкам**, **челленджи** («портфель месяца»), **подписка на портфель инвестора**. Это даёт социальный эффект без модерации личных сообщений.

Если всё же делаем полноценную соцсеть — это отдельный продукт: оценка **2–4 недели** только на минимум (посты+комментарии+лента+подписки+жалобы) плюс постоянные расходы на модерацию и юридику (152-ФЗ / GDPR: согласия, удаление данных, хранение).

## Мои идеи, которых не было в списке

1. **Единый слой данных с провайдерами и fallback** (`quote`: Finnhub → Yahoo; `crypto`: Binance → Bybit; `RU`: MOEX ISS → Tinkoff/Invest API). Circuit breaker: провайдер отвалился — переключаемся и показываем бейдж «источник: Yahoo». Без этого каждая новая фича будет ломаться от чужого 403/429.
2. **Серверный торговый движок + журнал транзакций.** Сделки как API, `orders` и `trades` в БД, пересчёт позиций из журнала (а не хранение `totalCost`), сверка `cash`. Это же закрывает читерство лидерборда.
3. **Базовая валюта и FX.** Портфель в USD, RUB, EUR на выбор; курсы ЦБ РФ / ECB раз в день; каждая сумма с валютой и курсом.
4. **Прозрачность данных.** `asOf`, `source`, `delayed: true` для MOEX. Маленький бейдж «15 мин» — и продукт перестаёт врать.
5. **`/api/health` + метрики провайдеров** (ошибки, p95, кэш-хиты) и лог всех внешних ошибок. Мы сегодня потеряли полдня только потому, что `catch {}` глотает всё: сломанные БД, MOEX, крипта и валюта выглядели как «пустые данные».
6. **Тесты на расчёты** (vitest): P&L, средняя цена, частичная продажа, исполнение лимитных заявок, индикаторы. Это дешёвые тесты, которые ловят именно те баги, что я нашёл (P1-11, P0-5).
7. **Уведомления вместо соцсети:** алерт «AAPL +5%», «заявка исполнена», «P/E выше исторической медианы». Email/telegram-бот — дешевле и полезнее постов.
8. **Демо-режим и онбординг:** 5 экранов «что такое P/E, RSI, диверсификация» на реальных данных — прямое продолжение идеи №4 и сильный аргумент для новой аудитории.
9. **Дисклеймер и правовой минимум:** «симулятор, не инвестиционная рекомендация», политика конфиденциальности, согласие на обработку данных — до публичного запуска, не после.
10. **Убрать OneDrive из рабочего пути.** Проект с `node_modules` в синхронизируемой папке — источник конфликтов и медленного старта; `.env` в облаке — лишний риск. Перенести в `C:\dev\stock_analyzer`, а `.env` держать вне репозитория с `.env.example`.

## План по фазам

### Фаза 0 — «Стабилизация» (2–3 дня) ✅ без неё нельзя двигаться дальше

Цель: приложение не врёт, не падает и не течёт.

1. Исправить `SUPABASE_URL`, добавить health-запрос БД на старте, логировать ошибки Supabase.
2. Убрать `password` из всех ответов, `.select('*')` → явные поля, `/api/leaderboard` — публичные поля.
3. Аутентификация: Supabase Auth (или bcrypt + httpOnly-сессии), middleware, `/api/*` защищённые, rate limit на auth.
4. Валидация входных данных (zod): email, пароль, `shares > 0`, `target_price > 0`, `portfolio` по схеме.
5. `ws.on('error')`, `try/catch` на `JSON.parse`, backoff, ping/pong; на клиенте — реконнект с индикатором «нет связи».
6. MOEX: корневой сертификат Минцифры через `NODE_EXTRA_CA_CERTS` + `httpsAgent`; честный `percent` из `PREVPRICE`/`LASTCHANGEPRC`.
7. Крипта: Binance REST как минимум (WS — в фазе 2), убрать FCS; FX — отдельный провайдер.
8. EU-фундаментал: либо починить Eulerpool (UA + обработка 403), либо временно скрыть блок, а не показывать «—» как данные.
9. Вычистить мёртвые тикеры (`LVMH.PA`, `UG.PA`, `POLY`, `AGRO`, `DZRL`, `VSMZ`, `ELTZ`), 404 на неизвестный символ вместо `price:0`.
10. `exportCSV`, объём в индикаторах, живой гейдж, честная средняя цена после продажи, `return_percent` только после загрузки котировок.

**Критерий приёмки:** регистрация/логин/выход работают; чужой портфель изменить нельзя; `/api/quote/RU/SBER`, `CRYPTO/BTCUSDT`, `FOREX/EURUSD` отдают реальные данные; сервер переживает 429 и обрыв WS; в ответах API нет ни одного пароля.

### Фаза 1 — «Данные и графики» (3–4 дня)

1. Слой провайдеров + fallback + circuit breaker, `asOf`/`source` в каждом ответе.
2. Кэш: single-flight, negative caching, правильные TTL, метрики.
3. lightweight-charts вместо CanvasJS/Chart.js: свечи + объём + MA, таймфреймы, кроссхэйр, тема.
4. Валюты: базовая валюта, FX-курсы, корректные символы в портфеле и тепловой карте.
5. Скелетоны + состояния «ошибка/пусто/retry» для всех блоков.
6. Серверный торговый движок: сделки через API, журнал, пересчёт позиций, `orders` с валидацией.

**Критерий приёмки:** график читаем как в TradingView; ни один блок не показывает «—» без причины; все суммы с валютой; лимитная заявка не может увести кэш в минус; P&L совпадает с пересчётом из журнала.

### Фаза 2 — «Аналитика, которую просят» (4–6 дней)

1. Глоссарий + попапы по метрикам (8 главных метрик в первой итерации, дальше расширять).
2. Карточка компании (профиль, сектор, капитализация, описание).
3. Сравнение двух тикеров: таблица + нормализованный график.
4. История P/E: реконструкция из EPS TTM, подпись «оценка», медиана сектора.

**Критерий приёмки:** клик по любой метрике открывает объяснение; сравнение работает для US/EU/RU с пересчётом валют; P/E-график не пустой на 3+ годах истории; крипта обновляется в реальном времени.

## Риски

| Риск | Что делаем |
|---|---|
| Finnhub 429 и лимит WS-символов | не подписываться на 50 символов; свой протокол подписок, backoff, кэш, платный тариф при росте |
| Binance недоступен из региона | абстракция провайдера + Bybit/OKX fallback |
| MOEX ~15 мин задержка | показывать `asOf` и бейдж задержки, не выдавать за realtime |
| CanvasJS лицензия | уйти на lightweight-charts (Apache-2.0) |
| Eulerpool/FCS нестабильны | вывести из критического пути, заменить, не строить на них фичи |
| Утечка секретов через OneDrive | перенести проект, `.env` вне синка, ротация ключей |
| 152-ФЗ/GDPR при запуске соцслоя | согласия, удаление данных, политика — до, а не после |
